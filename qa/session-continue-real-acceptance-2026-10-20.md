# 会话无感续接：真实环境验收

日期：2026-10-20。基线：`d220c1f0d`。本记录只描述验收结果和问题，没有修改代码。

## 环境与方法

- **应用**：当前分支构建的桌面应用，以开发模式启动。AgentKib 自己的数据（Electron 用户数据、运行时数据、`AGENTKIB_HOME`）全部放在临时目录，用户本机的 AgentKib 数据目录前后没有变化。
- **CLI**：Claude Code 2.1.303 和 Codex 0.155.1 沿用用户自己的配置目录，因为登录凭据会轮换，复制到沙盒会让原登录失效。
  - 测试会话只建在一个临时项目里，没有恢复或改动任何已有会话。
  - 终端里的 Claude 用 Haiku，Codex 用 `gpt-6-luna` 加低推理强度。
  - 启动应用和 CLI 前，清掉了外层 Claude Code 会话带来的 `CLAUDE*` 环境变量。
- **其他版本**：
  - 连接插件只认 Claude Code 2.1.301，所以第 2b 条另装了 2.1.301，用 `--plugin-dir` 只对单个会话加载，没有安装到 Claude Code 配置里。
  - 第 7 条另装了 Codex 0.146.1，低于最低支持版本 0.147.0。
  - 两者都装在临时目录。
- **手机**：用 Android 模拟器里的 Chrome，通过 `adb reverse` 连接桌面的本机网页服务（127.0.0.1:1421，不经过局域网或公网）。
- **驱动方式**：界面通过 CDP 操作，终端通过 tmux 操作。
- **未覆盖**：Windows、Codex 桌面应用（本机未安装）、真机手机。

## 缺陷（按严重程度）

### 1. Codex 续接在已登记工作区的根目录运行，不在会话自己的目录（严重）

**现象**：
- X4i 原本在测试项目里运行，AgentKib 续接的那一轮，记录里的 `cwd` 是 `/`，审批策略 `on-request`，沙盒 `workspace-write`。
- 前后两次终端轮次的 `cwd` 都是测试项目。
- 之后用 `codex resume` 打开时，Codex 会先询问"Choose working directory to resume this session"。

**原因**：
- 接管时，托管记录的 `workspace` 取的是已登记工作区的根目录，并且要求两者一致（`packages/backend/src/web-read.ts:3635-3652`）。
- 续接时，用它同时作为 `cwd` 和沙盒可写根目录（`web-read.ts:4737-4750`），会话自己的 `cwd` 没有被用上。
- 本次自动发现的工作区里有一个 `/`（侧栏名为"workspace"，包含 147 条会话），所以可写根目录变成了 `/`。

**影响**：
- 模型在错误的目录里工作。
- 当登记的工作区范围很大（`/`、主目录）时，沙盒的写入限制实际上失效。
- D11 让每次在空闲 Codex 会话里发消息都走这条路径，影响面比原来的手动"交给 AgentKib"大得多。

**修复方向**（需要确认）：
- 以会话自己的 `cwd` 作为 `cwd` 和可写根目录，并校验它位于已登记工作区之内；
- 已登记工作区是 `/` 或主目录时，不作为可写根目录。

### 2. 启动阶段失败后，会话被永久锁在"结果待确认"（严重）

**现象**：
- C1 第一次发送时机器负载约 190，Claude 握手超过 30 秒（`Claude initialize timed out`）。
- 消息其实没有发出，但会话停在"结果待确认"，"发送"一直禁用。
- 刷新记录、"会话操作 → 刷新"、重启应用都不能恢复。

**原因**：
- 用户消息要等握手成功后才写入（`claude-managed-runner.ts:1444-1491`）。
- 握手失败时，只有"进程根本没起来"这种情况会回到可重试状态；其余情况记为 `outcome-unknown`。
- 主机端只把 `ClaudeUndispatchedError` 视为"未派发"（`claude-managed-read.ts:806-821`）。
- 之后没有运行器、状态又不是 `idle`，于是一直按"结果未确认"处理（`:3133`）。

**附带文案问题**：横幅对所有 `outcome-unknown` 都显示"上次操作结果尚未确认。请先核对终端状态，再重新连接。"（`claude-session-banner.ts:16-20`，桌面和 Web 都是）。这个会话并没有连接终端，而且和上面"控制已暂停"那句重复。

**修复方向**：
- 消息未派发时，任何启动失败都按"未执行"处理，回到可重试状态并保留草稿；
- 对已经卡住的会话：如果记录的原因是启动失败，且台账里没有已派发的命令，就允许恢复；
- 后台运行的会话使用自己的提示文案。

### 3. Codex 分支后无法发送（严重）

**现象**：
- 选择"分支会话并继续"后，约 1 分钟才进入分支。期间依次出现"结果待确认"、英文原文 "Error: operation_busy" 和"会话目录刷新失败"。
- 在分支里两次发送都提示"本次操作未执行。请刷新状态后重试，不会自动重发。"，分支记录里没有任何消息。

**原因**：
- 后端以 `unsupported-model` 拒绝了发送。
- 分支继承了 `config.toml` 的默认模型 `gpt-6.1-sol`。这个模型 Codex CLI 可以用，但不在 app-server 的模型列表里。
- 界面只显示通用的"未执行"，没有说明原因，也没有引导用户改用其他模型。

**修复方向**：
- 说明原因，并提供切换"下一轮"模型的入口；
- 或者对 CLI 本身接受的配置模型放宽校验。

### 4. 跟随态的"停止当前轮次"不能打断终端（中，上一轮引入）

**现象**：已连接终端（插件不能发送）时，终端回复期间按钮可见。在终端那一轮进行到一半时点击，两次都没有任何反馈，终端那一轮照常跑完（33～34 秒）。

**说明**：
- 插件支持中断：`$.turn.abort`，要求 `turnId` 与当前轮次一致（`packages/claude-bridge-plugin/hooks/register.js:620-635`）。
- `control("stop")` 遇到未满足的条件会静默返回（`use-session-controller.ts:1619-1625`）。
- 现有证据还区分不了是"请求没发出"，还是"插件返回了冲突或失败"。
- 这个按钮是上一轮审查修复时放进跟随态的。

**修复方向**：
- 用 2.1.301 复现并定位原因；
- 修好之前，跟随态不显示"停止"，或者在失败时给出提示。

### 5. 打开已续接过的 Claude 会话，会常驻一个空闲进程（中）

**现象**：
- 页面停在会话上时，空闲 10 分钟的进程被收回，1 秒后又被重新拉起。
- 页头一直显示"在 AgentKib 中运行"，"已结束后台进程"的提示从来没机会出现。
- 这时在终端打开同一会话，会出现"AgentKib 已停止"的提示，但 AgentKib 当时并没有在运行任何一轮。
- 每个这样的进程还会连带启动用户配置的 MCP 服务。
- 离开页面后约 15 秒收回。
- 再次打开这类会话时，手机和桌面都会先闪现 2～7 秒"已结束后台进程，可以回 Claude Code 继续这条会话"，随后进程又被拉起，提示消失。这句话既不准确，又把用户引到别处。

**原因**：`settingsState` 为了读取模型和权限设置，会对已接管的空闲会话调用 `#prepareRunner` 启动 CLI（`claude-managed-read.ts:3768-3775`），界面每次刷新状态都会调用它。

**修复方向**：不要为了显示设置而启动进程；缓存上次读到的设置，等用户打开设置或者发送时再启动。

### 6～21. 其他偏差

6. **Claude 分支标题不对**：分支标题是 "Claude Code (fork)"，页面上没有选择条承诺的"分支自 {原标题}"。没有 AI 标题的会话，续接后标题会变成 "Claude Code"。这只是 AgentKib 的显示问题，原生记录没有被改写。Codex 分支正确显示了"分支自 …"。
7. **英文原始错误**："Error: operation_busy" 会在分支创建和发送启动时闪现，"会话目录刷新失败。 Error: operation_busy" 也会显示给用户。
8. **Claude 分支页的告警一直不消失**："请求失败，请检查连接或在桌面端查看详情。 重新连接"，同时"会话设置"显示"暂不可用"。
9. **分支按钮反复跳动**："分支会话并继续"会在可点和禁用之间来回切换，每次可点的时间只有 0.2～8 秒，手机和桌面不同步。点到禁用状态时没有任何反馈，看上去像是要等 12～40 秒才能点。
10. **跟随态闪烁**：每轮开始和结束时，页面会有 1～2 秒闪回"正在检查状态"，并重新出现输入框。
11. **Codex 仅可查看页的历史没有更新**：缺少终端那一轮，刷新后仍缺。
12. **分支在列表里重复出现**：重启后，Codex 分支在列表里出现两行（"未分类"和"workspace"），磁盘上只有一个。
13. **列表行没有"仅可查看"**：Codex 版本过低时，列表行不显示"仅可查看"，和修订计划 8.2 的表格不一致；目录展示不探测版本，需要决定是否在列表上显示。
14. **连接终端对话框的状态让人误解**：在生成连接码之前，对话框显示"仅可查看 · 需要 Claude Code 2.1.301"。
15. **Codex 选择条期间看不到草稿**：选择条替换输入框后，草稿看不到了。但手机复测确认，CLI 退出后草稿会原样恢复，所以没有丢失，只是缺少"草稿已保留"的提示。
16. **手机回复顺序闪错**：手机发送后，回复会先出现在用户消息上方约 2.4 秒，然后才恢复正确顺序。
17. **从其他 App 打开链接被拒**：用 Android intent 打开链接（比如扫码或在聊天软件里点链接）时，本机网页服务因 `Sec-Fetch-Site: cross-site` 返回 403，页面直接显示原始 JSON `{"error":"cross_site_request"}`，而手动输入地址可以正常打开。需要在真机以及局域网、托管入口上复核。
18. **手机和桌面的操作可用性不一致**：手机"会话操作"里的重命名、归档、分支会话、恢复队列都可以点；桌面在同一状态下是禁用的，并说明"主机未提供或尚未验证此能力"。
19. **"设置是否生效尚未确认"的提示时机不对**：Codex 终端退出后，输入框工具栏出现这句提示，但用户并没有改过设置。
20. **手机 412px 宽度下的布局问题**：
    - "会话设置"被截成"会…"；
    - "新建任务""搜索会话正文"只有 32px 高，低于 44px 的触控尺寸；
    - 权限模式警告占了 4 行，把输入框挤到下面。
21. **手机列表难用**：手机列表不会随会话更新而重新排序。续接过的 Claude 会话标题都是 "Claude Code"（见偏差 6），手机上无法按标题区分。

## 观察

- 在终端新建的会话，要手动刷新才会出现在列表里。
- `codex exec` 建的会话（`source=exec`）按现有规则不在列表里显示，所以本次的 Codex 用例改用交互式会话。
- `ps` 回退扫描会把命令行里含有 `claude … --resume <id>` 字样的任意进程当成占用者；本次一条 shell 命令就造成过一次误判。实际中这种情况少见。
- 加载约 2600 条会话、机器负载高时，渲染器点击响应常要 5 秒以上。手机打开 Codex 会话要 16～34 秒才出现占用状态，桌面约 13 秒；这段时间"发送"按钮一直是禁用的。
- 本机网页服务用一次性授权码配对，页面写明"即可直接连接，无需再次确认"，所以没有校验数字和桌面确认。这和局域网直连文档描述的流程不同，但符合页面说明。
- 手机路由是 `#/sessions/<id>`，桌面是 `#/sessions?sessionId=<id>`，两者不通用。

## 对用户环境的影响

- **新增的测试会话**：用户真实的 Claude Code 和 Codex 历史里，多了临时项目下的测试会话，包括 AgentKib 创建的两个分支。
- **CLI 正常运行带来的改动**：
  - 信任临时项目时，Claude Code 写入了一条信任记录；
  - Codex 交互界面启动时，更新了 `~/.codex/config.toml` 的修改时间（内容未查看）；
  - Claude Code 每次启动都会更新 `~/.claude/plugins` 的修改时间。
- **旧版 Codex 的影响**：沙盒应用带着 Codex 0.146.1 运行时，`~/.codex/skills/.system/` 被换成了 0.146.1 自带的系统技能。之后在第 8 条用例里启动 0.155.1 时，已按标记重新装回。
- **插件目录**：Claude Code 2.1.301 用 `--plugin-dir` 加载插件时，在被忽略的构建目录 `apps/desktop/build/claude-bridge/` 下生成了 `tsconfig.json` 和 `.claude-plugin/types/`。验收结束后已用 `claude:stage` 重建这个目录，生成的文件已经清掉。
- **收尾**：沙盒应用、模拟器、tmux 和测试用的 CLI 进程都已关闭；用户本机 AgentKib 的数据目录和 `~/.claude/settings.json` 前后没有变化。

## 修复要求与验收标准

### 必须修复（1～5）

**1. Codex 工作目录与可写范围**
- `cwd` 和沙盒可写根目录改用会话自己的目录（rollout 的 `session_meta.cwd`，或最近一次 `turn_context.cwd`），并校验它在托管记录的已登记工作区之内；不在其内就拒绝，并给出原因。分支（`thread/fork`）同样适用。
- 无论登记的工作区是什么，`/` 和用户主目录都不能作为可写根目录。
- 会话自己的目录就是 `/` 或主目录时，按"仅可查看"处理并写明原因：新增原因码，四种语言都要有文案。
- 会话目录已经不存在时，明确报错，不要回退到工作区根目录。
- 验收：
  - 续接 X4i 这类会话后，记录里的 `turn_context.cwd` 等于会话目录；
  - 之后 `codex resume` 不再询问工作目录；
  - 测试覆盖 `/`、主目录、子目录、目录不存在四种情况。

**2. 启动失败后永久锁住**
- 只要用户消息还没派发，启动阶段的任何失败（握手超时、握手前进程退出或断流、写入握手请求失败），在确认进程树已结束后，都要回到发送前的状态，并保留原因和草稿。主机端结果记为 `not-dispatched`，并结束这条命令。
- 已经卡住的记录：如果原因属于上面这类启动失败，台账里没有已派发的命令，也没有运行器，就自动恢复为可发送。其他 `outcome-unknown`（已派发的轮次、设置确认超时）保持不变。
- 后台运行的会话处于 `outcome-unknown` 时，不显示"请先核对终端状态，再重新连接"，也不要重复"控制已暂停"那句。四种语言都要改。
- 验收：
  - 模拟握手超时：界面显示"本次操作未执行"，输入框可用并保留草稿，再次发送成功；
  - C1 这类已经卡住的记录，重启后能恢复；
  - `claude-frame-drift-process.test.ts` 现有的断言仍然通过。

**3. Codex 模型不在列表里时发不出**
- 先确认 app-server 是否接受"不在 `model/list` 里、但 CLI 配置能用"的模型（例如本次的 `gpt-6.1-sol`）。如果接受，就不要拦截来自用户配置或会话记录的模型，只校验用户在"下一轮"里主动选的模型。
- 分支沿用源会话的模型和推理强度，不要用配置的默认值。
- 确实需要拦截时，给出具体原因，并直接提供切换"下一轮"模型的入口，不要只显示通用的"本次操作未执行"。
- 验收：在配置默认模型不在列表里的环境下，分支后能发送并收到回复；或者用户看到具体原因，改了模型后能发送成功。

**4. 跟随态的停止**

### 第 17 项实施前安全评估

当前服务在静态页面与接口分流之前拒绝 `Sec-Fetch-Site: cross-site`，因此从外部 App 导航也无法打开页面。拟仅对路径严格为 `/` 或 `/index.html`、方法为 GET/HEAD、同时具有 `Sec-Fetch-Mode: navigate` 和 `Sec-Fetch-Dest: document` 的主页面导航豁免这一项检查。应用使用 hash 路由，无需扩大到任意静态路径。

安全影响限定为允许其他网站或 App 打开不包含私有会话数据的应用外壳。Host 和 Origin 的既有校验、接口鉴权、配对、Cookie、CSRF、权限与协议检查继续生效；`/api/*`、assets、iframe/object、fetch/XHR、POST 以及不符合导航元数据的请求不享受例外。CSP 的 `frame-ancestors 'none'` 和 referrer 策略保持不变。

本机入口与配置的外部 HTTPS 入口需分别验证允许导航和拒绝矩阵。LAN listener 本身不托管页面，页面由托管入口提供；LAN 接口的 Origin、Bearer、CSRF 和预检校验不变，应分别验证托管页面导航与连接后的 LAN 请求。合成 HTTP 测试不能替代 Android intent/扫码实测；实际元数据若不符合上述条件，应先记录原因，不自动扩大豁免范围。
